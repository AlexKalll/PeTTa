What is PeTTa?

PeTTa = Efficient MeTTa language implementation in SWI-Prolog

  • MeTTa is an S-expression-based AI/reasoning language (like Lisp)
  • PeTTa compiles MeTTa directly into Prolog clauses
  • Runs at near-native Prolog speed
  • Supports: NARS, PLN reasoning, atom spaces, Python interop

    # Run a MeTTa file
    time sh run.sh ./examples/nars_tuffy.metta

Prolog Crash Course (1/10)

Facts, Rules, and Predicates

Prolog programs = statements of truth, not instructions. No loops, no if-else — just what is true.


      % A FACT is always true — like a row in a database table
      parent(john, mary).      % Always, unconditionally true

      % A RULE is conditionally true — :- means "IF"
      grandparent(X, Y) :-
          parent(X, Z),        % IF X is parent of Z
          parent(Z, Y).        % AND Z is parent of Y

      % A QUERY asks for solutions
      % ?- grandparent(john, X).
      % → X = ann

A predicate = name + arity (# of args): parent/2 and parent/3 are completely different predicates!

How PeTTa Uses This

Atom spaces ARE Prolog predicates:


        MeTTa:  (parent Alice Bob)
        Space:  '&self'(parent, alice, bob).
        % This is a FACT! Stored with assertz.
      

        MeTTa:  (match &self (parent $who Bob) $who)
        % Translates to Prolog QUERY:
        % ?- '&self'(parent, who, bob).
        % → who = alice

Function registration uses arity:


        register_fun(myfunc),                % Marks myfunc as callable
        assertz(arity(myfunc, 3)).            % myfunc/3 (2 inputs + output)
        % The translator checks this to generate the right call!

The translator internally uses current_predicate(Fun/Arity) to decide if it can call a function directly at compile time or needs runtime dispatch. Arity is how Prolog distinguishes different overloads — a function with 2 args is a completely separate thing from one with 3.

Prolog Crash Course (2/10)

Unification (=)

Unification is NOT assignment. It's a bidirectional constraint that makes both sides identical.


      % If X is unbound: X = hello  →  X is now bound to hello
      % If X is already 3: X = 5  →  FAILS (3 ≠ 5)
      % This is NOT "x = 5" in Python — there's no overwriting!

      [H|T] = [a, b, c].
      % H = a, T = [b, c]  — destructures AND constructs

      3 = X + 1.
      % FAILS! Unification is SYNTACTIC, not arithmetic.
      % It tries to make 3 identical to +(X, 1), which is impossible.

Think of it like Python's structural pattern matching: match [a, b, c]: case [first, *rest]: ...

How PeTTa Uses Unification

1. Pattern matching in spaces:


        (match &self (parent $who Bob) $who)
        % $who unifies with each first argument of parent/2 facts
        % Unification finds all bindings that make it true

2. Let bindings:


        (let $x (+ 1 2) (+ $x 1))
        % Translates to: X = 3, then Out is X + 1
        % $x unifies with 3 via the = operator

3. The translator itself:


        % translate_clause uses unification to destructure:
        Input = [=, [F|Args0], BodyExpr]
        % This unifies F with the function name,
        % Args0 with the argument list,
        % BodyExpr with the body — all in one step!

Key insight:

In PeTTa's translator, unification is the primary tool — pattern matching MeTTa ASTs, extracting function names and args, binding variables. The entire translate_expr pipeline is driven by unification, not function calls.

Prolog Crash Course (3/10)

Variables and Anonymous Variables

Variables = uppercase or underscore. Atoms (constants) = lowercase. This is the opposite of most languages!


      parent(john, mary).  % john and mary are ATOMS (constants)
      parent(John, mary).  % John is a VARIABLE (matches anything)

      % The anonymous variable _ : each _ is INDEPENDENT
      parent(_, _).
      % Means "someone is parent of someone"
      % The two _ can be different people — they're unique vars

      % In queries, _ means "I don't care what this is"
      % ?- parent(john, _).
      % → true  (we don't care which child)

This is like Python's _ convention in unpacking: first, *_, last = items — but in Prolog, each _ is guaranteed independent, not just convention.

How PeTTa Uses Variables

MeTTa $x → Prolog variable X:

The parser (parser.pl) converts $x to a Prolog variable. All occurrences of $x in the same expression share the SAME variable:


        MeTTa: (= (myfunc $x) (+ $x 1))
               ↓ parser
        Prolog: [=, [myfunc, X], [+, X, 1]]
               ↓ translator
        Clause: myfunc(X, Out) :- Out is X + 1.

Anonymous variable use in spaces:


        (match &self (parent $who _) $who)
        % Find all parents — we don't care about the child

Translate args with _ for unused:


        % When compiling, the parser uses _ for repeated $_
        % MeTTa: (f $_ $_)  →  Prolog: [f, _, _]
        % The two _ are DIFFERENT variables — no relationship!

Prolog Crash Course (4/10)

Lists

Prolog lists use [a, b, c] but are linked lists underneath, not arrays. The | separates head from tail.


      [1, 2, 3]  % Syntactic sugar for .(1, .(2, .(3, [])))
                  % Like Lisp's (cons 1 (cons 2 (cons 3 nil)))

      % Head/Tail decomposition:
      [H|T] = [a, b, c].  % H = a, T = [b, c]

      % Multiple extraction:
      [A, B|Rest] = [1, 2, 3, 4].  % A=1, B=2, Rest=[3,4]

      % Lists can be nested, mixed types:
      [a, [b, c], 42, "hello"]

Python equivalent: first, *rest = [1, 2, 3] — but Prolog's unification works both ways: [H|T] = [1, 2, 3] gives you H=1, T=[2,3], AND [1|[2,3]] = [1, 2, 3] is true.

How PeTTa Uses Lists

THIS IS THE MOST IMPORTANT INSIGHT:

All MeTTa S-expressions become Prolog lists:


        MeTTa:  (+ 1 2)            →  Prolog: [+, 1, 2]
        MeTTa:  (parent Alice Bob) →  Prolog: [parent, alice, bob]
        MeTTa:  (= (f $x) (+ $x))  →  Prolog: [=, [f, X], [+, X]]

The parser converts text to lists. The translator walks these lists to generate goals. The choice between "this is code" vs "this is data" depends on whether the first element is registered as a function.


        % In spaces.pl — storing atoms:
        add_sexp(Space, [Rel|Args]) :-
            Term =.. [Space, Rel | Args],  % Build space predicate
            assertz(Term).                  % Assert as fact

        % In translator — head/tail destructuring:
        translate_expr([H|T], Goals, Out) :-
            % H is the function name (like +, if, match, etc.)
            % T is the argument list

List operations in MeTTa (car-atom, cdr-atom, cons-atom) are direct wrappers around Prolog's [H|T] unification. When you see (cons-atom H T) in MeTTa, it's literally just Prolog's [H|T] under the hood.

Prolog Crash Course (5/10)

Cut (!)

Cut tells Prolog: "commit to this choice, don't try alternatives". Like break + return in a loop.


      max(A, B, A) :- A >= B, !.   % If A >= B, commit (don't try next clause)
      max(_, B, B).                 % Only reached if A < B

      % Without cut:
      % ?- max(5, 3, X).  →  X = 5 ;  X = 3  (WRONG — two answers!)
      % With cut:
      % ?- max(5, 3, X).  →  X = 5  (only one — correct)

Cut prevents backtracking — Prolog's built-in search for alternative solutions. After cut, Prolog discards all choice points created since the parent goal was called.

Two types of cuts: green cuts (don't change logical meaning, just optimize) and red cuts (change logical meaning — use carefully).

How PeTTa Uses Cut

1. The cut operator in MeTTa:


        ;; Translates directly to Prolog's !/0
        (let $temp (cut) 42)
        ;; → Once we reach this, commit to current bindings
      

        % In translator.pl (line 115):
        ; HV == cut, T = [] -> append(GsH, [(!)], Goals),
        % Just generates a Prolog cut!

2. Preventing choice points in Prolog-backed libraries:


        'write-stream'(Name, Content, true) :-
            open_stream(Name, Stream), !,
            write(Stream, Content).
        % Without cut: if write fails, it backtracks to find
        % another open_stream/2 fact — WRONG behavior!

3. In the type system:


        'get-type'(X, 'Number')   :- number(X), !.
        'get-type'(X, 'String')   :- string(X), !.
        'get-type'(X, 'Bool')     :- member(X,[true,false]), !.
        'get-type'(X, '%Undefined%').  % Default fallback
        % Cuts ensure we stop at the FIRST matching type
        % —without them, a number could also match '%Undefined%'

4. In match/case semantics:


        (case (superpose (1 2 3))
              ((1 "one")
               (2 "two")
               (3 "three")))
        % cut ensures: once a branch matches, stop looking

Prolog Crash Course (6/10)

assertz / retractall

Modify Prolog's database of facts and rules at runtime. Like appending to or clearing entries from a global list.


      assertz(Clause).     % Add clause at the END
      asserta(Clause).     % Add clause at the BEGINNING
      retractall(Pattern). % Remove ALL clauses matching Pattern

      % Example:
      assertz(my_pred(hello)).          % Database now has my_pred(hello)
      assertz(my_pred(world)).          % my_pred(hello), my_pred(world)
      retractall(my_pred(_)).            % Remove all my_pred clauses

Python equivalent: manipulating a module-level list of registered items. assertz = db.append(clause), retractall = db[:] = [c for c in db if not matches(pattern, c)].

Critical: Only works for predicates declared :- dynamic. Static predicates can't be modified at runtime.

How PeTTa Uses assertz / retractall

1. Adding atoms to spaces:


        add_sexp(Space, [Rel|Args]) :-
            Term =.. [Space, Rel | Args],
            assertz(Term).  % Add as a space fact

        % MeTTa: (add-atom &self (parent Alice Bob))
        % → assertz('&self'(parent, alice, bob))

2. Compiling MeTTa functions to Prolog:


        'add-atom'(Space, Term, true) :-
            Term = [=,[FAtom|W],_], !,  % It's a function definition
            once(translate_clause(Term, Clause)),  % Compile to Prolog
            assertz(Clause, Ref),                  % Assert compiled clause
            assertz(translated_from(Ref, Term)).
            % Ref lets us find and remove it later

3. Function registration:


        register_fun(N) :-
            (fun(N) -> true      % Skip if already registered
                      ; assertz(fun(N)) ).  % Add to registry

4. Removing atoms and functions:


        remove_sexp(Space, [Rel|Args]) :-
            Term =.. [Space, Rel | Args],
            retractall(Term).  % Remove all matching atoms

        'remove-atom'(Space, Term, true) :-
            findall(Ref, translated_from(Ref, Term), Refs),
            forall(member(Ref, Refs), erase(Ref)),  % Erase compiled clauses
            retractall(translated_from(_, Term)).    % Clean tracking

Why Ref matters:

assertz(Clause, Ref) returns a Ref handle. This is how PeTTa can later erase(Ref) to remove a specific compiled clause — like tracking object references for cleanup. Without it, you'd have to retractall, which removes too much.

Prolog Crash Course (7/10)

Dynamic Predicates

Declares: "this predicate will change at runtime". Without this, Prolog assumes clauses are fixed after loading.


      :- dynamic my_store/2.   % Declaration — must be at compile time

      % Now you can modify it at runtime:
      assertz(my_store(key, value)).
      retractall(my_store(_, _)).
      my_store(key, Value).  % Querying also works

      % Without :- dynamic:
      % assertz(my_store(key)) → ERROR! Can't modify static predicate

Why it's needed: Prolog compilers optimize static predicates for fast lookup. Dynamic predicates use a different internal representation that supports runtime modification at a small performance cost.

Python equivalent: a module-level variable my_store: dict versus a frozen types.MappingProxyType. Dynamic = mutable, static = frozen.

How PeTTa Uses Dynamic Predicates

Dynamic predicates are EVERYWHERE in PeTTa:

The space system itself:

When you write '&self'(parent, alice, bob), &self is effectively a dynamic predicate. Every named space becomes a dynamic predicate. The space system implicitly relies on the Prolog database being dynamic — if spaces were static, you couldn't add facts at runtime.


        % Library state pattern — always use :- dynamic:
        :- dynamic(counter/1).
        'inc-counter!'(Name, true) :-
            retract(counter(Name, Old)),  % Remove old value
            New is Old + 1,
            asserta(counter(Name, New)).   % Store new

Key Rule:

If your Prolog-backed library holds state, declare :- dynamic. Forgetting this is the #1 cause of silent failures in Prolog-backed libraries.

Prolog Crash Course (8/10)

nb_setval / nb_getval (Non-Backtrackable Storage)

Global key-value storage that survives backtracking. Normal variables lose bindings on backtrack — nb_* values persist.


      nb_setval(counter, 0).        % Set global value — overwrites
      nb_getval(counter, N).        % Retrieve current value
      nb_delete(counter).           % Remove entirely

      % Key difference from assertz:
      % nb_setval stores ONE value per key (like a dict)
      % assertz accumulates MANY clauses (like a list)

      % Key difference from normal variables:
      % Normal: X = 1 ; fail. → X is unbound again
      % nb: nb_setval(x, 1) ; fail. → x is STILL 1

Python equivalent: a module-level dict that persists regardless of exceptions or control flow.

Why "non-backtrackable"? When Prolog backtracks (trying alternative solutions), normal variable bindings are undone. nb_* values are stored in the global environment, not on the stack, so they survive.

How PeTTa Uses nb_setval / nb_getval

1. Function meta-clause storage:


        % In translate_clause (translator.pl:23-24):
        catch(nb_getval(F, Prev), _, Prev = []),
        nb_setval(F, [fun_meta(Args1, BodyExpr) | Prev]).
        % Each new (= (F ...) ...) definition appends a meta-clause
        % This is how PeTTa handles MULTIPLE definitions of the
        % same function (like pattern matching clauses)!

2. Lambda counter:


        % In translator.pl (lines 432-435):
        next_lambda_name(Name) :-
            catch(nb_getval(lambda_counter, Prev), _, Prev = 0),
            N is Prev + 1,
            nb_setval(lambda_counter, N),
            format(atom(Name), 'lambda_~d', [N]).
        % Each (|-> ($x) ...) gets a unique name like lambda_1
        % Counter survives backtracking — no duplicate names!

3. Specialization flag:


        % In specializer.pl (line 42):
        nb_getval(specneeded, true),
        % Only proceed if specialization actually helped
        % Set by var_use_check (line 79):
        nb_setval(specneeded, true)
        % When a variable is detected as a function head call

4. State variables in MeTTa:


        ;; MeTTa interface to nb_setval/nb_getval:
        ^(change-state! &myvar myvalue)   % nb_setval(&myvar, myvalue)
        (get-state &myvar)                 % nb_getval(&myvar, Value)
        (bind! &myvar ['new-state', X] Y)  % nb_setval(&myvar, X) → Y
      

        % Implementation in metta.pl (lines 240-242):
        'bind!'(A, ['new-state', B], C) :- 'change-state!'(A, B, C).
        'change-state!'(Var, Value, true) :- nb_setval(Var, Value).
        'get-state'(Var, Value) :- nb_getval(Var, Value).

When to use nb_* vs assertz:

Use CaseToolWhy
Single global value (counter, flag, registry)nb_setvalOverwrite semantics, fast access
Collection of facts (space atoms, clauses)assertz/retractallMultiple entries, pattern-based query

Prolog Crash Course (9/10)

call/1 and =../2 (Univ)

call/1 = dynamic goal invocation. =../2 = convert between term and list form. Together they make Prolog homoiconic — code is data.


      % =.. ("univ") converts term ↔ list:
      Term =.. [hello, a, b].
      % Term = hello(a, b)  — construct from list

      hello(a, b) =.. [Name|Args].
      % Name = hello, Args = [a, b]  — deconstruct to list

      % call/1 runs a term as a goal:
      Goal = hello(world),
      call(Goal).  % Same as: hello(world)

      % Combined:
      Goal =.. [my_pred, X],  % Construct goal dynamically
      call(Goal).             % Execute it

Python equivalent: getattr(module, "func_name")(*args) for call, and [func.__name__, *func.args] for univ. But Prolog's version is simpler and built into every term.

How PeTTa Uses call/1 and =../2

1. The TRANSLATOR uses =.. to build calls:


        % When translating (myfunc $a $b):
        % Known function → construct predicate call
        append(AVs, [Out], CallArgs),      % Add output var at end
        Goal =.. [Fun|CallArgs],           % Build myfunc(a, b, Out)
        append(Inner, [Goal], Goals)       % Add to goal list

2. The RUNTIME uses call/1 to execute goals:


        % In metta.pl (lines 245-250):
        eval(C, Out) :-
            translate_expr(C, Goals, Out),  % Get goal list
            call_goals(Goals).               % Execute each

        call_goals([]).
        call_goals([G|Gs]) :-
            call(G),          % Execute one goal
            call_goals(Gs).   % Continue with rest

3. reduce/2 uses it for runtime dispatch:


        % translator.pl (lines 50-58):
        reduce([F|Args], Out) :-
            % If F is registered AND has a defined predicate:
            current_predicate(F/Arity), ...
            append(Args,[Out],CallArgs),
            Goal =.. [F|CallArgs],    % Build goal dynamically
            catch(call(Goal),_,fail)  % Execute with error handling

        % This is how PeTTa handles function calls when the
        % function name is only known AT RUNTIME.

4. Typed dispatch uses it:


        % When multiple types exist for the same function,
        % =.. builds different branches:
        typed_functioncall_branch(Fun, TypeChain, ...) :-
            % Each branch calls the same Fun but with
            % different type-checking goals prepended
            build_call_or_partial(Fun, AVs, Out, ...).

Why this matters:

Without call/1 and =../2, PeTTa could not dynamically compile MeTTa code at runtime. They are the bridge between "MeTTa code as data (lists)" and "Prolog code as executable predicates." Every (match ...), every (reduce ...), every lambda invocation uses these two constructs internally.

Prolog Crash Course (10/10)

term_variables/2

Extracts all Prolog variables from a term into a list in order of first appearance, deduplicated. Like walking an AST and collecting every identifier.


      term_variables(Term, Vars).
      % Vars = [all variables in Term, first-appearance order]

      % Example:
      term_variables( (parent(X, Y), grandparent(Y, Z)), Vars).
      % Vars = [X, Y, Z]

Python has no direct equivalent because Python doesn't track variables as first-class objects you can enumerate. The closest is the inspect module or AST walking — but Prolog makes variable introspection trivial.

This is a unique Prolog superpower. No other mainstream language gives you direct access to the variable structure of any expression.

How PeTTa Uses term_variables/2

1. Lambda compilation — the KEY use case:


        % translator.pl (lines 237-252):
        ; HV == '|->', T = [Args, Body] ->
          next_lambda_name(F),
          term_variables(Body, AllVars),      % ALL vars in body
          term_variables(Args, ArgVars),       % Only arg vars
          exclude({ArgVars}/[V]>>
                    memberchk_eq(V, ArgVars),
                  AllVars, FreeVars),          % What's left = FREE vars
          append(FreeVars, Args, FullArgs),    % Capture + args
          translate_clause([=, [F|FullArgs], Body], Clause),
          ...
          ( FreeVars == [] -> Out = F          % No closure needed
                            ; Out = partial(F, FreeVars) )  % Closure!

When you write (|-> ($x) (+ $x $y)), $y is a free variable — it must be captured from the surrounding scope. term_variables detects this.


        MeTTa:  (|-> ($x) (+ $x $y))
                ↓
        AllVars = [X, Y]     (all vars in the body)
        ArgVars = [X]         ($x is the argument)
        FreeVars = [Y]        ($y captured from environment!)
                ↓
        Out = partial(lambda_1, [Y])  A CLOSURE carrying Y

2. Let/Chain variable tracking:


        % In let translation — variables in patterns work via
        % Prolog's built-in variable sharing, but term_variables
        % is used for more complex pattern analysis

3. The sealed construct:


        ; HV == sealed, T = [Vars, Expr] ->
          translate_expr_to_conj(Expr, Con, Val),
          Goals = [copy_term(Vars, [Con, Val], _, [Ncon, Out]), Ncon]
          % Makes a COPY of all variables — isolates computation

Why this is critical for PeTTa:

Lambdas with free variables = closures. Without term_variables/2, PeTTa couldn't distinguish between argument variables (bound) and environment variables (captured). Every lambda like (|-> ($x) ($f $x)) where $f comes from outside relies on this analysis to become a partial(F, [f]) closure at runtime. The distinction between F (a plain callable) and partial(F, Bound) (a closure carrying captured values) is entirely driven by term_variables/2.

Prolog-Backed: File I/O Example


      % lib_fileio.pl — Prolog predicates in function convention

      :- dynamic(open_stream/2).  % Stateful stream registry

      % Simple file write
      'write-file'(File, Content, true) :-
          resolve_export_path(File, AbsPath),
          open(AbsPath, write, Stream),
          write(Stream, Content),
          close(Stream).

      % Named stream operations
      'open-writer'(Name, File, true) :-
          resolve_export_path(File, AbsPath),
          open(AbsPath, write, Stream),
          asserta(open_stream(Name, Stream)).

      'write-stream'(Name, Content, true) :-
          open_stream(Name, Stream), !,
          write(Stream, Content).

      'close-stream'(Name, true) :-
          open_stream(Name, Stream), !,
          close(Stream),
          retractall(open_stream(Name, _)).

      ;; Step-by-step (from lib_import.metta):
    

      (= (import_prolog_functions_from_file
              $prologfile $importfunctions)

         (let* (($prologfile (exists_file))    ;; 1. Check file exists
                ($prologfile (consult))         ;; 2. Load .pl → assert all predicates
                ($function                      ;; 3. Non-deterministically
                  (superpose $importfunctions)));;    iterate function names
                (import_prolog_function         ;; 4. Register each as MeTTa func
                  $function)))

import_prolog_function(F) calls register_fun(F)

The Translation Layer

The heart of PeTTa — translator.pl

translate_expr/3


      % Input:  MeTTa S-expr as Prolog list [F|Args]
      % Goals:  Prolog goals to execute
      % Out:    Output variable

      translate_expr(Input, Goals, Out)
    

      MeTTa:  (+ 1 2)
      List:   [+, 1, 2]

      translate_expr([+, 1, 2], Goals, Out) →
        Goals = ['+'(1, 2, Out)]
        Out = 3

Translator: Clause Compilation

translate_clause/2 — converts (= ...) into Prolog clauses


      MeTTa:  (= (myfunc $x) (+ $x 1))
      Input:  [=, [myfunc, x], [+, x, 1]]

      translate_clause(Input, Clause) →
        Clause = (myfunc(X, Out) :- '+'(X, Out))
        Which is Prolog: myfunc(X, Out) :- Out is X + 1.
    

      % The actual code:
      translate_clause(Input, (Head :- BodyConj)) :-
          Input = [=, [F|Args0], BodyExpr],
          constrain_args(Args0, Args1, _GoalsA),
          translate_expr(BodyExpr, GoalsBody, ExpOut),
          append(Args1, [Out], FinalArgs),
          Head =.. [F|FinalArgs],
          goals_list_to_conj(GoalsBody, BodyConj).

Translator: Dispatch Logic

When translating [H|T], the translator checks (in order):

  1. Translator rules — custom hooks via translator_rule/1
  2. Non-determinism — superpose, collapse, cut, once
  3. Sequential — progn, prog1
  4. Conditionals — if, case
  5. Binding — let, let*, chain
  6. Lambdas — |-> (compiled to new Prolog predicate)
  7. Spaces — match, add-atom, remove-atom
  8. Manual dispatch — call, reduce, eval, quote
  9. Smart dispatch (default) — registered fun → call, else → data

Smart Dispatch: The Key Decision


      % The critical decision point in translate_expr:

      % Registered function → direct Prolog call
      ( atom(HV), fun(HV) ->
        append(AVs, [Out], CallArgs),
        Goal =.. [HV|CallArgs],
        append(Inner, [Goal], Goals)

      % Atom that's NOT a function → data list (keep as-is)
      ; atomic(HV), \+ fun(HV) ->
        Out = [HV|AVs],
        Goals = Inner

      % Unknown → runtime dispatch
      ; append(Inner, [reduce([HV|AVs], Out)], Goals) )

This is why register_fun is critical!

Function Registration System

Why Registration Matters


      % Without register_fun:
      (my-func 3 5)  →  treated as DATA [my-func, 3, 5]

      % With register_fun:
      (my-func 3 5)  →  Prolog call: my-func(3, 5, Out)
    

      :- dynamic fun/1.            % Database of registered function names

      register_fun(N) :-
          (fun(N) -> true          % Skip if already registered
                    ; assertz(fun(N)) ).   % Mark as callable

      % Also stores arity for validation:
      assertz(arity(my-func, 3)).  % 2 inputs + 1 output

Automatic vs. Manual Registration

Automatic


          ;; = definition auto-registers:
          (= (my-func $x) (+ $x 1))
          ;; ↓
          register_fun(my-func)

Manual


          ;; Must register Prolog predicates:
          ^(import_prolog_function my-func)
          ;; ↓
          import_prolog_function(F) :-
              register_fun(F).

Without registration, the translator generates a data list, not a function call!

The Atom Space System

Spaces = Prolog dynamic predicates (just collections of facts)


      % An atom (parent Alice Bob) is stored as:
      '&self'(parent, alice, bob).

      % The space system asserts/retracts these:
      add_sexp(Space, [Rel|Args]) :-
          Term =.. [Space, Rel | Args],
          assertz(Term).

      remove_sexp(Space, [Rel|Args]) :-
          Term =.. [Space, Rel | Args],
          retractall(Term).

      'get-atoms'(Space, Pattern) :-
          current_predicate(Space/Arity),
          functor(Head, Space, Arity),
          clause(Head, true),
          Head =.. [Space | Pattern].

How add-atom Handles Functions


      % When adding a function definition (= ...):
      'add-atom'(Space, Term, true) :-
          Term = [=,[FAtom|W],_], !,  % It's a function!
          add_sexp(Space, Term),       % Store in space
          register_fun(FAtom),          % Mark as callable
          length(W, N),
          Arity is N + 1,
          assertz(arity(FAtom, Arity)),
          once(translate_clause(Term, Clause)),  % Compile to Prolog
          assertz(Clause, Ref),
          assertz(translated_from(Ref, Term)),
          invalidate_specializations(FAtom).

      % Regular data atoms (not functions):
      'add-atom'(Space, Term, true) :-
          add_sexp(Space, Term).        % Just store in space

The Space Predicate Pattern


      MeTTa:  (parent Alice Bob)
      Space:  '&self'(parent, alice, bob)

      MeTTa:  (= (double $x) (+ $x $x))
      Space:  '&self'(=, [double, x], [+, x, x])

      MeTTa:  (: double (-> Number Number))
      Space:  '&self'(:, double, [->, Number, Number])

Everything in MeTTa is stored as a space predicate:


      '&self'(Data, Args...).

      % Data = atom name (parent, =, :, etc.)
      % Args = rest of S-expression

The Type System

Type Annotations


      (: + (-> Number Number Number))
      (: my-function (-> String String Bool))

Stored in &self as: '&self'(:, my-function, [->, String, String, Bool])


      % Dynamic type resolution
      'get-type'(X, 'Number')   :- number(X), !.
      'get-type'(X, 'String')   :- string(X), !.
      'get-type'(X, 'Bool')     :- member(X, [true, false]), !.
      'get-type'(X, 'Symbol')   :- atom(X), \+ fun(X), !.
      'get-type'(X, 'Expression') :- is_list(X), !.
      'get-type'(X, '%Undefined%').  % Default fallback

      % When a function has type annotations, the translator

      typed_functioncall_branch(Fun, TypeChain, T, Out, BranchGoal) :-

Higher-Order Function Specialization

specializer.pl

Optimizes higher-order functions by creating specialized versions


      ;; MeTTa: (map-atom (|-> ($x) (+ $x 1)) (1 2 3))
      ;; Without specialization: runtime dispatch each iteration
      ;; With specialization: compiles a dedicated predicate

      ;; The specializer detects this and creates:
      map-atom_Spec_[+]([1,2,3], Out) :-
          maplist([X, Y]>>(Y is X + 1), [1,2,3], Out).

How Specialization Works


      1. Detect call: map-atom(Func, List)
         where Func is a registered fun (like +)

      2. Extract meta-clauses for map-atom

      3. Find specializable higher-order variables
         (variables used as function heads in the body)

      4. Build specialization name:
         map-atom_Spec_[+]

      5. Compile new Prolog clause with Func
         substituted at call sites

      6. Register and assert the specialization
    

      % The specialization name encodes the concrete args:
      format(atom(SpecName),
             "~w_Spec_~w", [HV, CleanBindSet])
      % → map-atom_Spec_[+]

Complete Pattern: Creating a Stateful Library


      % lib_counter.pl

      :- dynamic(counter/1).          % Mutable state
      :- dynamic(counter_history/2).  % Log

      'make-counter!'(Name, Start, true) :-
          asserta(counter(Name, Start)).

      'inc-counter!'(Name, true) :-
          retract(counter(Name, Old)),
          New is Old + 1,
          asserta(counter(Name, New)),
          asserta(counter_history(Name, New)).

      'get-counter'(Name, Value) :-
          counter(Name, Value).
    

      ;; lib_counter.metta
      ^(import! &self (library lib_import.metta))
      ^(import_prolog_functions_from_file
          (library lib_counter.pl)
          (make-counter! inc-counter! get-counter))

      ;; Usage:
      ^(make-counter! "my-counter" 0)
      ^(progn ^(inc-counter! "my-counter")
              ^(inc-counter! "my-counter")
              (get-counter "my-counter"))  ;; → 2

Best Practices

Prolog Predicate Design

  • Function convention: Last argument = output, preceding = inputs
  • Determinism: Succeed exactly once (use !/0 where needed)
  • Side effects: Return true for commands: 'my-cmd'(Arg, true)
  • No dangling choice points: Use cut or once/1
  • Atom names: Quote with '...' if containing special chars

MeTTa Library Design

  • Always annotate public functions: (: foo (-> Type1 Type2 Ret))
  • Group related functions with a prefix: PLN.Derive, Truth_Revision
  • Handle errors with catch / case
  • Pure functions in MeTTa, side-effecting in Prolog

Error Handling Patterns


      ;; Safe division
      (= (safe-divide $a $b)
         (if (> $b 0)
             (/ $a $b)
             (empty)))

      ;; Call with fallback
      (= (call-with-fallback $fn $arg)
         (case (catch ($fn $arg))
               (((Error $type $ctx) "Error occurred")
                ($result $result))))

      ;; Using case + Empty
      (= (lookup $key $alist)
         (case (match &self (pair $key $value))
               (((pair $k $v) $v)
                (Empty "not found"))))

Performance Considerations

  • Prolog layer is faster than pure MeTTa for hot code
  • static-import! loads large data much faster than import!
  • collapse collects all results into memory — use foldall for aggregation
  • foldall aggregates without materializing — more memory efficient
  • Ensure tail recursion in recursive MeTTa functions

      ;; Efficient: foldall counts without listifying
      (= (match-count $space $pattern)
         (foldall + (match $space $pattern 1) 0))

      ;; Less efficient: collapse lists everything
      (= (match-list $space $pattern)
         (collapse (match $space $pattern $x)))
